## วิธีทดสอบ

- นิสิตจำลอง N คน (Node + supabase-js) ทำแบบเดียวกับหน้าเว็บจริง:
  - ล็อกอินด้วยรหัสนิสิต
  - subscribe `problem-state` เสมอ และ `problem-counts` เฉพาะโหมด realtime (โหมด polling ถามตัวนับทุก 5 วินาที)
  - รอ broadcast เปิดข้อ แล้วส่ง `submit_answer` ณ เวลาสุ่มภายใน 60 วินาที
- อาจารย์จำลอง 1 คนใช้ service key subscribe `problem-submissions:<id>`
- ตรวจ 8 ข้อ:
  - ส่งสำเร็จครบ
  - จำนวนแถวในฐานข้อมูลถูกต้อง
  - `submission_count` = N
  - `submit_order` = 1..N ไม่ซ้ำ
  - อาจารย์เห็นครบ
  - ทุกคนได้ broadcast เปิดข้อ
  - ทุกคนได้ broadcast ปิดข้อ
  - ตัวนับฝั่งนิสิตถึง N

## สิ่งที่พบ

1. **กฎที่บังคับที่ฐานข้อมูลถูกต้องทุกรอบ** ส่งครบ, ตัวนับตรง, ลำดับไม่ซ้ำ แม้ส่งพร้อมกัน 150 คน
2. **เพดานข้อความต่อวินาทีของ Realtime** แผนฟรีมีเพดาน 100 ข้อความ/วินาที:
   - Supabase บนเครื่องบังคับเพดานนี้จริง: เกินแล้ว (`too_many_requests`) ข้อความ**ทุกช่อง**ถูกทิ้ง ไม่ใช่แค่ตัวนับ
   - บน project จริง โหมด realtime 100 คน (fan-out เฉลี่ยราว 170 ข้อความ/วินาที) ไม่ถูกทิ้งเลย
   - Supabase ไม่ได้บอกวิธีนับเพดานต่อวินาทีบน cloud ไว้ชัดเจน จึงยังไม่รู้ว่ารับได้สูงสุดเท่าไร
3. **โควตาข้อความต่อเดือน** แผนฟรีได้ 2 ล้าน ทั้งผู้ส่งและผู้รับนับทุกคน (ตามเอกสาร Supabase “Manage Realtime Messages usage”)

   | ต่อ 1 ข้อ, นิสิต 110 คน | realtime | polling |
   | --- | --- | --- |
   | ตัวนับ (`problem-counts`) | ≈ 110 × 111 = 12,210 | 0 |
   | เปิด/ปิด + อาจารย์ | ≈ 440 | ≈ 440 |
   | **รวม** | **≈ 12,650** | **≈ 440** |
   | 3 ข้อ/คาบ × 4 คาบ/เดือน | ≈ 152,000 (7.6% ของโควตา) | ≈ 5,300 (0.3%) |

   ตัวนับแบบ realtime โตตาม N² ถ้าทั้งเทอมมี 4 ตอนรวม 440 คน จะใช้ราว 600,000 ข้อความ/เดือน (30% ของโควตา) ยังพอ
4. **Polling** 110 คนสร้างคำขอราว 22 ครั้ง/วินาทีขณะเปิดหน้าโจทย์ ฐานข้อมูลรับได้ ผิดพลาด 0 แต่ p95 ของการส่งคำตอบช้ากว่ารอบ realtime (1.0 กับ 0.37 วินาที)
5. **เพดานล็อกอินของ Auth** ล็อกอินด้วยรหัสผ่าน (`/auth/v1/token?grant_type=password`) นับใน **Token refresh** ไม่ใช่ Sign-ups and sign-ins (ตามเอกสาร Supabase “Auth rate limits”)
   - เป็น token bucket ต่อ IP: เก็บได้ 30 ครั้ง แล้วเติมตามค่าที่ตั้ง
   - ค่าปัจจุบัน 1800/5 นาที = **6 ครั้ง/วินาที ต่อเนื่อง + เร่งพร้อมกันได้ 30 ครั้ง**
   - ตรงกับที่วัดได้: ยิง ~50/วินาที ผ่าน 56 คนในราว 4 วินาทีแรก
   - เพดานนี้ไม่ขึ้นกับแผน (Free/Pro เหมือนกัน) และปรับใน Dashboard ได้
   - **2026-11-11 ปรับเป็น 6000/5 นาที (20/วินาที)** แล้ววัดซ้ำด้วย `loadtest/login-burst.mjs` 110 คนกดเข้า 50 คน/วินาที:
     - ผ่านครั้งแรก 60 คน, อีก 50 คนโดนเพดานแล้วลองใหม่ทุก 1 วินาที
     - **ทุกคนเข้าครบใน 6.2 วินาที** (ส่งคำขอรวม 202 ครั้ง) ตรงกับถัง 30 + 20/วินาที
     - ค่าเดิม 1800 คำนวณได้ราว 14 วินาที
   - ล็อกอินของนิสิตทำผ่าน server action บน Vercel ทั้งห้องจึงใช้เพดานก้อนเดียวกันไม่ว่าออกเน็ตทางไหน
   - หน้าเว็บแสดง “มีการเข้าสู่ระบบจำนวนมากเกินไป กรุณารอสักครู่แล้วลองใหม่” แล้วกดซ้ำได้
   - session อยู่ได้นาน (refresh token) จึงหนักเฉพาะคาบแรกหรือหลังออกจากระบบ
6. **การเชื่อมต่อพร้อมกัน** 100–110 คน + อาจารย์ ต่ำกว่าเพดาน 200 ของแผนฟรี
   - นิสิตที่เปิดหลายแท็บหรือหลายเครื่องนับเพิ่มคนละ 1
   - 2 ตอนเรียนพร้อมกัน (220 คน) จะเกินเพดาน

## หน้าเปิดค้างเกินอายุ JWT

เทสต์ `e2e/session-expiry.spec.ts` รันเฉพาะเมื่อสั่ง วิธีรันเขียนไว้ในไฟล์

- **ตั้งค่า:** บนเครื่องตั้ง `jwt_expiry = 60` แล้วเปิดหน้านิสิตและหน้าอาจารย์ค้างไว้ 150 วินาที (2.5 เท่าของอายุ) โดยไม่รีโหลด
- **ผล 2026-11-11 ผ่าน:**
  - นิสิตเห็นโจทย์เปิดเอง
  - ส่งผ่านหน้าเว็บได้ใบยืนยัน
  - อาจารย์เห็นการส่งแบบ realtime
  - ทั้งสองฝั่งเห็นปิดข้อ
- **ข้อสรุป:** คาบที่ยาวเกิน 1 ชั่วโมงไม่มีปัญหาเรื่อง session
